# Markup View Framework Architecture Project - Full Handover

## Project Background

Markup View Framework, identified as MVF, is a framework-class library that provides an architecture optimized for developing Windows GUI applications.

MVF is NOT an application. MVF is a framework for building Windows GUI applications.

MVF is NOT a CodexCLI client. A CodexCLI client may later be developed as a separate application that uses MVF, but that client is outside the current MVF scope.

The architecture is based on WPF, while the client area is built with WebView2 inside the XAML/WPF window framework.
Project history note:

- A CodexCLI client was an earlier application idea.
- During environment and architecture discussion, the priority shifted to creating the user's own optimal Windows GUI development framework first.
- MVF started as that framework effort.
- Any CodexCLI client should be treated only as a possible future consumer application of MVF, not as MVF itself.
- For current MVF design work, CodexCLI-specific requirements should be ignored unless explicitly reintroduced.

The primary motivation is:

- Provide an optimal architecture for the user's Windows GUI application development
- Use WPF as the native window shell and XAML-side host framework
- Build the client UI area with WebView2, HTML, CSS, and DOM control
- Obtain Unity-like runtime control feeling
- Avoid conventional WPF/MVVM framework-driven architecture
- Maintain direct C# ownership over runtime UI behavior
- Preserve explicit runtime control and predictability

The project is currently Windows-only.

Cross-platform support is NOT a design goal at this stage.

The development environment is:

- Rider
- .NET
- WPF
- WebView2

# Why Existing WPF/MVVM Approaches Were Rejected

The user strongly prefers:

- Explicit runtime control
- Imperative UI manipulation
- Runtime-owned UI state
- Predictable update flow
- Unity/WinForms-like mental model

The user intentionally avoids:

- DataBinding-centric architecture
- DependencyProperty-centric architecture
- DataContext-driven design
- Framework-owned synchronization
- Reactive UI systems
- Virtual DOM style rendering ownership
- Automatic MVVM toolkit assumptions

The project intentionally treats WPF as a thin shell only.

## C# to JS Invocation Model

The current C# to JS invocation style uses WebView2 script execution from C#.

Typical flow:

- C# prepares a purpose-specific bridge call as a string
- `WebView2.ExecuteScriptAsync(...)` sends the bridge call into the loaded page
- JS exposes callable entry points under `window.MVF.dom`

Example JS-side entry points currently used by the framework:

- `window.MVF.dom.loadStyle(...)`
- `window.MVF.dom.loadJS(...)`
- `window.MVF.dom.setHtml(...)`

This is a direct script-injection style bridge, not a host-object RPC model.
No host object binding is currently required for the existing flow.

The `MVFViewCanvas` DOM bridge script is stored separately in
`src/UI/JS/MVFViewCanvasDom.js` and injected into the HTML canvas template at
load time.

`MVFController` creates the WebView2 host, assigns it to `MVFNode.WebView`,
and keeps the `MVFViewCanvas` DOM node handle after the canvas HTML has been
navigated and the DOM is available.

`MVFNode` does not expose a generic JavaScript execution surface.
Instead, node-targeted operations are limited to purpose-specific bridge
methods such as `SetHtmlAsync(...)`, `SetContextAsync(...)`, and
`GetContextAsync(...)`.

The node-level flow is:

- `MVFController` creates the WebView2 host
- `MVFController` assigns that host to `MVFNode.WebView`
- `MVFController` loads the canvas HTML together with its CSS and JS set
- `MVFController` resolves the `MVFViewCanvas` DOM node and keeps its handle
- `MVFNode.SetHtmlAsync(...)` serializes its handle and updated HTML
- `window.MVF.dom.setHtml(...)` targets a DOM node through its handle, not
  through `data-ui-id`
- `MVFNode.Find(...)` is the node lookup API and replaces any previous
  `MVFController.Find(...)` responsibility

# Window Composition

MVF windows are composed with XAML/WPF as the native window framework.

The basic window structure contains three regions:

- Header region
- Client region
- Footer region

Header region:
- Hosts menus, toolbars, command bars, and other upper window UI.
- Belongs to the WPF/XAML side.
- Concrete content, size, visibility, layout, and style are customized by the consumer-side View definition.

Client region:
- Hosts the actual application runtime UI area.
- Uses WebView2-based client content.
- HTML/CSS/DOM define the visible UI inside each WebView2 client content.
- C# owns runtime state, orchestration, and DOM control.
- In the current initialization flow, `MVFController` receives the placement
  container, connects `MVFClientArea` into `MVFRoot.xaml`'s
  `MVFClientAreaHost`, and then acquires the WebView instance from
  `MVFViewHost` inside `MVFClientArea`
- After acquiring `MVFViewHost`, `MVFController` loads the `ViewCanvas` HTML
  together with its CSS and JS set into the WebView2 runtime
- The `MVFViewCanvas` DOM node is resolved only after the `ViewCanvas` HTML
  has been navigated and the DOM is available. The controller keeps that node
  handle instead of attaching a separate `MVFViewCanvas` component.

Footer region:
- Hosts status bars, notifications, progress indicators, and other lower window UI.
- Belongs to the WPF/XAML side.
- Concrete content, size, visibility, layout, and style are customized by the consumer-side View definition.

MVF must not fix concrete Header/Footer design or region sizes. These belong to the View customization layer.

## Client Content Model

The Client region is not limited to a single fixed WebView2 instance.

MVF should support one or more WebView2-based client contents and allow the active client content to be switched, such as with tabs.

Multiple HTML-based client contents may coexist in the same window.

The preferred model is:

- A WPF/XAML ClientHost owns the client content collection and active selection.
- Each client content may own its own WebView2 runtime when persistent independent state is required.
- The framework may also provide a lighter navigation/swap model for simple cases, but it must not replace the persistent multi-content model.
- Tab headers, selection UI, and presentation style are View concerns and should remain customizable.
- C# remains the owner of client content lifecycle, state, and DOM access routing.

# Architectural Philosophy

The architecture intentionally resembles Unity-style UI control.

Preferred style:

```csharp
await Dom.SetTextAsync(...);
await View.RefreshAsync();
```

The architecture prioritizes:

- Explicit updates
- Direct control
- Scoped DOM access
- Runtime ownership
- Predictability
- Local UI hierarchy control

The architecture intentionally avoids automatic synchronization systems.

# DOM Philosophy

The DOM is treated similarly to a Unity hierarchy.

Example:

LoginForm
 ├ UserName
 ├ Password
 └ Submit

Preferred access style:

```csharp
var form = Dom.Scope(UiId.LoginForm);

await form.SetValueAsync(UiId.UserName, "abc");
await form.SetValueAsync(UiId.Password, "1234");
```

Scoped DOM access is preferred.

However, `data-ui-id` must NOT be treated as a required identifier for every
HTML element.

Only root-level or otherwise important larger UI units should be required to
have stable externally-addressable identifiers such as `data-ui-id`.

Smaller child elements should normally be found from inside the parent
Component's DOM scope by local search such as `name`, role-like attributes,
or other suitable local selectors.

MVF should avoid turning the entire HTML tree into a globally-addressed ID map.

Node identity rules:

- HTML `id` and MVF node identity are separate concepts
- In MVF, `data-ui-id` is treated as the node ID
- In MVF, `data-ui-name` is treated as the node name
- `data-ui-id` is the externally addressable identifier used for MVF node
  lookup and handle acquisition
- `data-ui-name` is the externally addressable name value used for MVF lookup
  and display-oriented node naming
- The HTML `id` attribute, if used, remains a separate HTML concern and is not
  the MVF node ID
- `data-ui-id` is preferred when a UI unit should be explicitly addressable,
  but it is not mandatory for every element
- `data-ui-name` follows the same overall policy as `data-ui-id`
- When explicit MVF addressing is not needed, HTML `id` may be used as a
  simpler alternative
- If `data-ui-id` is not present, MVF may fall back to the HTML `id` attribute
  as a secondary lookup key
- If `data-ui-name` is not present, MVF may also fall back to the HTML `id`
  attribute as a secondary lookup key for name-oriented use
- The fallback `id` lookup is secondary and should not replace `data-ui-id` as
  the preferred MVF identifier
- If a request would normally modify an `id`, MVF should modify `data-ui-id`
  instead when the intent is to address the MVF node identity
- If `data-ui-id` does not already exist on the target element, MVF should add
  it
- If `data-ui-name` does not already exist on the target element, MVF should add
  it when a name is needed
- `id` should not be rewritten as a substitute for MVF node identity changes
- MVF may reference the HTML `id` attribute in read-only fashion
- `data-ui-id` is the MVF override target for node identity changes
- `data-ui-name` is the MVF override target for node name changes
- `id` remains a read-only HTML-side reference, while `data-ui-id` is the
  MVF-side identity value that may be added or changed
- `id` remains a read-only HTML-side reference, while `data-ui-name` is the
  MVF-side name value that may be added or changed

When a parent Component finds a child node and wants to attach another
Component instance to that exact node, MVF may use a JS-side runtime node
handle system.

In that model, JS keeps the actual DOM node reference and C# holds only a
handle or scope-like wrapper that resolves back to that node through the JS
bridge.

Those handles are runtime references, not durable HTML identifiers.

If a parent DOM region is replaced, the child handles under that replaced
region should be treated as invalid and reacquired explicitly.

# MVVM Interpretation

The project still broadly follows MVVM principles, but with a custom interpretation.

Model:
- data
- state
- business control

ViewModel:
- UI state management
- UI coordination
- feature orchestration

View:
- HTML
- XAML
- Prefab
- display definition itself

C# UI classes are NOT considered the View itself.

C# UI classes are closer to:

- ViewController
- UI runtime controller
- View connector

ViewModel is NOT required to map 1:1 with View.

## Root Module Exception

`MVFRootModule` is the ViewModel for the MVF root control written in XAML.

This module is a special root-level exception because its direct target is a XAML control.

Other UI modules should primarily follow the normal MVF direction:

- C# owns runtime state and orchestration
- WebView2 hosts client content
- HTML/CSS/DOM define client UI structure and presentation
- JS acts only as a DOM driver and event forwarder

The root module exists to connect the XAML-side MVF root control with the runtime module structure.

The basic XAML framework area should be placed under `MVF.UI.Frame`.

`Frame` is a category name that means the UI framework / structural frame, similar to how `Core` can name a foundational category.

Types or XAML files inside this namespace do not need to repeat `Frame` in their names unless the type itself specifically represents a frame.

For example, the root XAML should be named `MVFRoot.xaml`, not `MVFRootFrame.xaml`, because `Frame` is the containing category rather than the direct object name.

XAML files under `MVF.UI.Frame` must not have code-behind `.xaml.cs` files unless WPF makes them absolutely unavoidable.

In MVF's design philosophy, the UI should ideally be written entirely in HTML.

HTML View is not just another View option; it is the intended primary UI definition layer and is treated as the more capable replacement for XAML in MVF.

XAML exists only because WPF requires it for the native window itself and for the minimal non-client / host-side framework structure outside the WebView2 client area.

Therefore the question is not whether XAML should contain behavior.

The stronger rule is that XAML itself should not exist unless it is required by WPF integration.

When XAML is unavoidable, it should be kept to the minimum structural WPF host definition needed to compose the window, regions, and WebView2 host.

Runtime behavior, state, orchestration, and connection logic should live in MVF modules and runtime systems, such as `MVFRootModule`, not in `.xaml.cs`.

The `MVF.UI.Frame` namespace should contain only the XAML required to place the broad content frame inside the WPF window.

It should not define concrete application layout beyond the minimum host-side composition required by WPF.

The client area frame should directly host WebView2 as `MVFViewHost`.

`MVFViewHost` is the WPF/WebView2-side host that displays the HTML View.

The basic visual layout should be controlled by CSS in the consumer application's View folder.

Application-side HTML/CSS Views own the layout and presentation of the actual application UI.

The MVF HTML root should be named `MVFViewCanvas`.

`MVFViewCanvas` is the HTML/DOM-side root canvas loaded into the WPF/WebView2 host.

MVF should not define or manage the consumer application's CSS structure.

The MVF-provided `MVFViewCanvas.css` should only provide the minimum initial values required for the HTML view root to fill the WebView2 surface.

Consumer applications may organize and load their own CSS freely.

`MVFRootModule` may provide CSS loading methods so application-side C# control can add application CSS after `MVFViewCanvas` is loaded.

## HTML View Loading Model

The preferred MVF UI construction model follows the user's Unity workflow.

In Unity, the user does not statically place UI in the Scene view.

The user creates UI components separately and places them at runtime by loading Prefabs during startup and control flow.

MVF should follow the same mental model.

The initial frame HTML should act like a runtime scene root / canvas target, not like a fully statically composed screen.

Application modules are loaded and controlled by C#.

`MVFController.LoadModuleAsync<T>()` is the application-side module bootstrap
entry point.
It creates a module instance and runs its initialization flow.

During module initialization:

- The module resolves the UI it needs.
- Required Widgets are created or acquired.
- The module pushes the required HTML into the `MVFViewCanvas` drawing area.
- The module uses MVF node operations to update the canvas content in a
  controlled, scoped manner.

This means the framework minimum set is now:

- WPF host composition
- WebView2 canvas loading
- MVF node lookup by handle
- node-scoped HTML replacement
- module loading and initialization
- CSS / JS loading for the canvas surface

Modules should not be imported or owned by the frame HTML.

Instead, C# loads modules and then flows the required child View / Prefab HTML content into the frame HTML in order.

The frame HTML may provide broad insertion points, but it should not own module composition.

The default `MVFViewCanvas` HTML is framework-level infrastructure and belongs to the MVF library, not to each consumer application.

Consumer applications should provide Components and module control code, but
should not duplicate the common MVF frame HTML.

HTML View fragments below the module level may be treated like Prefab units.

These smaller View / Prefab units can be loaded into the current DOM hierarchy as directed by C#.

In consumer applications, `UI/Modules` is for ViewModel / module control code and must not be placed under `View`.

The consumer application View folder should be named `UI/View`, not `UI/Views`.

`UI/View` should contain View-side assets such as `Frame`, `Widgets`, and
`Components`.

`Widgets` and `Components` are View construction units below the module control
layer.

`UI/View/Widgets` should place widget HTML files directly under the folder without per-widget subfolders.

Widgets and Components are role-based classifications, not a strict mandatory
hierarchy.

A Widget does not have to be composed only from child Components that each map
to separately identified HTML roots.

The current design direction is that the minimum ViewModel/UI-controller unit is
`Component`.

`Widget` is not a fundamentally different controller type from `Component`.

Instead, Widget should be treated as a larger or more root-facing Component
concept when that name is useful at the View naming layer.

The old `Part` concept is removed.

Modules may operate root-facing Components, including Components whose View-side
HTML files are categorized as Widgets.

A parent Component may directly operate small internal elements inside its own
DOM scope without turning all of them into independently addressed Components.

Names such as `MVFDemoMainWidget`, `MVFDemoMainPanel`, and `MVFDemoMainContent` should be interpreted as the `Widget`, `Panel`, or content area belonging to the `MVFDemoMain` concept.

They must not be interpreted as establishing generic concepts named `MainWidget`, `MainPanel`, or `MainContent`.

Similarly, the current sample structure with a `header` and `MVFDemoMainContent` area is only an example of one Panel's internal DOM.

It does not define a required Panel structure.

Component internals are free and should be designed according to the actual UI concept.

A Widget HTML usually describes the placement structure for the larger
Component-level unit it represents.

However, a Widget is not required to place only separately attached child
Components.

For a small Widget, it is acceptable for the parent Component to directly
operate its internal inputs, buttons, messages, and other child elements
without introducing additional child Components for every small node.

When a Component exists only for one Widget, placing it under `UI/View/Components/{WidgetName}` is natural and preferred for clarity.

Files under `UI/View/Components` should not mechanically add `Component` to
their file names.

Those folders are categories, while each file should be named after the actual UI concept it represents, such as `Form`, `Panel`, or another natural control name.

Components may more naturally have Widget-specific subfolders because a Component may reasonably exist only for one Widget.

`Widget` is different because Widget is an established MVF view control concept and may be included in Widget file names.

Reusable generic controller classes such as text box Components may be attached
after a parent Component finds the target child nodes.

That attachment should not require every target node in the document to expose a
global identifier.

The parent Component should be able to find child nodes within its own local DOM
scope and then attach reusable MVFComponent-derived controllers to those nodes.

## MVFNode and MVFComponent Relationship

`MVFNode` is the runtime-side node host that represents a specific DOM node
through a JS bridge handle or equivalent runtime node reference.

`MVFComponent` is a C# runtime controller attached to one `MVFNode`.

The relationship is intentionally close to a Unity-style `GameObject` and
`Component` model:

- `MVFNode` owns the runtime node handle
- `MVFNode` stores attached `MVFComponent` instances
- `MVFComponent` keeps a back-reference to its bound `MVFNode`
- a Component operates its target DOM area through the node it is attached to

The current design direction is:

- one `MVFComponent` instance belongs to exactly one `MVFNode`
- one `MVFNode` may hold multiple Components
- Components on the same Node are distinguished by their concrete C# type
- the same concrete Component type should not be attached more than once to the
  same `MVFNode`

`MVFNode` should be treated as the attachment point and lifetime owner for
node-local Components.

`MVFNode` itself is not a customization target. It is created as part of the
DOM bridge flow and is intended to carry only a node handle or equivalent
runtime reference for the DOM node it represents.

When a Node is discarded, the attached Components under that Node should also be
treated as no longer valid.

When a DOM region is reacquired after replacement, a new `MVFNode` and new
Component attachments may be required rather than assuming the old runtime
attachments remain valid.

`MVFNode` does not necessarily have to own a `WebView2` instance directly.
The important requirement is that it can reach the WebView2-backed DOM runtime
through a bridge, host context, or equivalent runtime reference.

`MVFNode` may be created after a DOM node is found by JS and its handle is
returned to C#.

The intended flow is:

- JS searches the DOM by hierarchy navigation or `data-ui-id`
- JS resolves a specific DOM node
- JS associates that node with a runtime handle
- C# receives the handle and creates or updates the corresponding `MVFNode`
- `MVFNode` uses that handle to target the exact DOM node for later operations

`MVFNode` does not carry arbitrary custom data for user-defined behavior. Its
role is the runtime identification and access wrapper for a DOM node plus its
attached Components.

The exact handle representation is still undecided on the JS side, so the C#
side may temporarily use `object` for the handle type until the JS runtime
implementation is finalized.

The search model is intentionally close to Unity:

- `MVFNode.Find(...)` acts like `GameObject.Find`
- A `data-ui-id`-addressable Widget or other larger UI unit is the primary
  target for direct lookup
- `MVFNode.Find(...)` first searches `data-ui-id` and falls back to the HTML
  `id` attribute when needed
- Once a larger UI unit is found, smaller child UI elements are searched from
  that `MVFNode` by hierarchy traversal
- This hierarchy traversal is intended to behave like `Transform.Find`
- The direct `Find` model is intended for relatively large UI feature units,
  especially Widget-level UI
- Smaller UI elements are normally not addressed directly from the root and are
  instead resolved through the parent `MVFNode`

Handle lifecycle rules:

- When JS finds a DOM node by search, it stores the node in a handle list and
  returns the handle to C#
- After that, `MVFNode` can use its own handle to instruct JS which DOM node to
  target uniquely
- The JS bridge maintains a handle registry and resolves `MVFNode` operations
  through that registry
- `MVFNode` is the public-facing bridge entry point for node-targeted JS
  execution
- Any extra per-node runtime data should be stored as virtual data associated
  with the handle, not as an HTML attribute such as `data-ui-value`
- Handle-associated virtual data is runtime-only state and should be managed by
  the JS bridge alongside the handle registry
- The runtime-only per-handle virtual data is called `context`
- `context` is stored as part of the handle registry entry and is not exposed
  as an HTML attribute
- `MVFNode` should provide get/set access to the associated `context`
- If HTML is rewritten and a region is replaced, all handles within the replaced
  region are discarded
- If a DOM node is removed, that node's handle is also discarded
- Discarded handles must be reacquired before the related node can be used again

JS remains only the DOM driver that performs insertion, mutation, and event forwarding.

# Library Direction

The framework itself is the core product: a reusable WPF/WebView2-based Windows GUI application development framework-class library.

Current stance:

- WPF-only is acceptable
- Cross-platform abstraction is NOT required
- Premature generalization should be avoided

The framework is positioned as:

"WPF-based, WebView2-client-area, C#-centric Windows GUI application framework"

The foundation library should provide:

- WebView2 hosting
- DomDriver
- DomScope
- DomHandle or equivalent runtime node reference mechanism
- JS/C# bridge
- Event bridge
- ViewComponent base systems
- UiId systems
- Runtime lifecycle systems

The foundation library should NOT contain:

- App-specific screens
- Consumer-application-specific workflow logic
- Business logic
- Concrete UI implementations

Optional reusable controls may later become separate libraries.

# Web Reuse Philosophy

The project does NOT currently target Web deployment.

However:

- HTML
- CSS
- DOM structure
- data-ui-id structure

are intentionally kept reusable as design assets.

The user currently does NOT want to complicate the architecture for future web migration.

Therefore:

- JS may remain WebView2-specific
- Web migration would later rebuild JS/ViewModel structure separately
- Only the design/UI layer is expected to be reused

This is intentional.

# Coding Rules Context

A separate coding rules document already exists.

That document should be treated as the primary coding standard.

The coding rules are extremely important because:

- The architecture intentionally differs from standard WPF culture
- Naming meaning is prioritized heavily
- Framework drift must be avoided
- C# UI controller interpretation is non-standard
- MVVM interpretation is customized
- Unity-style runtime philosophy is important

Important interpretations:

- Code should read naturally as English
- Meaning > mechanical naming
- virtual = optional extension point
- abstract = required responsibility
- OnXxx = processing when Xxx occurs
- OnXxx is NOT event firing
- Base classes should work correctly without override
