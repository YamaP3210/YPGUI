# C# コーディング規約（現時点版）

## 基本方針

- 明示していない部分は原則として C# 標準規約に準拠する。
- ソリューションルートの `.editorconfig` は Rider に設定している C# コーディングスタイルの基本設定として扱う。
- `.editorconfig` と本規約が異なる場合は、本規約を優先する。
- コードは「文章」として読めることを重視する。
- 可読性は「短さ」ではなく「意味の明確さ」と「文章としての自然さ」を優先する。
- 略記は許可するが、可読性を損なう略語の使用は原則として避ける。
- 名称が過度に長くなりコード全体の可読性を損なう場合は、適切な略語を許可する。
- 文脈上明確な主語・目的語は省略してよい。
- ただし、意味が曖昧になる単語のみの命名は避ける。
- 名称は、機械的な命名パターンではなく、英単語・英文としての意味・文法・慣用性を優先して決定する。
- 名称は、単体で意味・意図・責務が理解できることを重視する。
- 統一性は重視するが、英語として不自然な名称を強制してまで優先しない。

---

# ソリューション・名前空間

## ソリューション識別子
現時点の本プロジェクト定義:

- 正式名称: Markup View Framework
- ソリューション識別子: MVF
- ルート名前空間: MVF
- 型名・識別子のルートには `MVF` をそのまま使用する。
- 例: `MVFWindowRoot`, `MVFClientHost`, `MVFDomDriver`
- `MvfWindowRoot` のように PascalCase 化して小文字化しない。

- ソリューションには正式名称と略称を定める。
- 略称はソリューション識別子として扱う。
- 略称は 2～4 文字程度、原則 3 文字とする。
- 略称は全て大文字とする。
- 略称は namespace・型名・識別子のルートとして使用する。

## ルート名前空間

- ルート名前空間はソリューション識別子をそのまま使用する。

## src フォルダ

- ソースコードなど開発部分のファイルは原則として `src` 配下へ配置する。
- `src` は物理構造用フォルダであり、名前空間には含めない。

## 名前空間とフォルダ構造

- 名前空間は原則として `src` 配下のフォルダ構造と一致させる。
- プロジェクト内の名前空間は原則としてプロジェクト名配下に置く。
- ただし、論理的位置・基礎性・利用文脈などに明確な理由がある場合は例外を許可する。
- 例外は「許可」であり「推奨」ではない。

## フォルダ命名

- フォルダ名は、役割と意味に応じて単数形・複数形を決定する。
- 同種クラス群を格納するフォルダは、原則として複数形を使用する。
- 概念領域・機能領域・基幹領域を表すフォルダは、単数形を使用してよい。
- 単数形・複数形は機械的に決定せず、英語としての自然さと役割構造を優先する。

---

# 型命名規則

## クラス

- クラス名は `ソリューション識別子 + PascalCase` とする。

## インターフェイス

- インターフェイス名は `I + ソリューション識別子 + PascalCase` とする。
- 外部ライブラリ・標準 API 側の命名規則には干渉しない。

## struct / record / delegate / enum

- struct / record / delegate / enum はクラスと同様の命名規則とする。
- enum 型名は単数形とする。

## generic 型パラメータ

- generic 型パラメータ名は、原則として `T` を使用する。
- 複数型パラメータを扱う場合や、役割差を明確化した方が可読性が高い場合は `TKey` `TValue` 等を使用してよい。

---

# ファイル命名

- ファイル名は、原則としてメインとなるクラス名と一致させる。
- ただし、可読性・責務・関連性などに明確な理由がある場合は例外を許可する。
- メインクラスと補助的な小規模クラスを同一ファイルへまとめてもよい。
- enum 定義群などを `XxxDefines` 等へまとめてもよい。
- 理由なくファイル名と内容の関連性が不明瞭になる構成は避ける。

---

# using とファイル内余白

- ファイル冒頭の `using` は、上から次の順で記述する。
  - .NET 関係の基本ライブラリ
  - メインに使用しているフレームワークやライブラリ
  - サードパーティのライブラリ
  - 当プロジェクトのライブラリ
- 各カテゴリの `using` 群の間は 1 行空ける。
- 該当する `using` が存在しないカテゴリは省略してよい。
- `using` の列挙からクラス名までは 5 行空ける。
- 同一ファイルに複数のクラスを記述する場合も、クラス同士の間は 5 行空ける。

---

# クラス内記述順

- クラス内のメンバは、原則として上から次の順で記述する。
  - イベント関係
  - delegate
  - 定数・列挙型定義など、定数系の宣言
  - 静的変数
  - 通常のメンバ変数
  - プロパティ
  - メソッド
- `static readonly` は定数系の宣言に含める。
- enum は private enum を通常の enum より前に記述する。
- プロパティは、indexer、静的プロパティ、通常プロパティの順で記述する。
- メソッドは、静的メソッド、通常メソッドの順で記述する。
- `operator` / `implicit` / `explicit` は、メソッドカテゴリ内で静的メソッドより前に記述する。
- コンストラクタ・デストラクタ・ファイナライザは、通常メソッドの先頭に記述する。
- 同一カテゴリ内のメンバ同士は 3 行空けて記述する。
- 例として、変数と変数の間、プロパティとプロパティの間、メソッドとメソッドの間は 3 行空ける。
- 別カテゴリのメンバ群同士は 5 行空けて記述する。
- 内部クラスは、最後のメソッドの後に 5 行空けて記述する。
- 内部 struct / record / interface は、内部クラスと同じ扱いとする。
- 拡張メソッドは、static class 内の静的メソッドとして扱う。
- 属性クラス / Attribute は、通常クラスと同じ扱いとする。
- partial メソッドは現時点では未定義とし、使用する必要が出た時点で配置と扱いを取り決める。
- primary constructor は、有用であれば使用してよい。言語仕様上クラス宣言部に記述するものとして扱い、通常のコンストラクタ配置ルールの例外とする。
- record の positional parameter は、有用であれば使用してよい。言語仕様上 record 宣言部に記述するものとして扱い、通常のプロパティ配置ルールの例外とする。
- 上記に分類しきれない要素の配置は、今後必要に応じて追記する。

---

# プロパティ

- プロパティ名は PascalCase とする。
- プロパティはクラスまたはインスタンスの状態・情報・属性を表現するために使用する。
- プロパティ名には名詞・形容詞・状態を表す語を使用する。
- 動作・命令・処理そのものを表す動詞的名称を使用してはならない。
- 利用者視点において、プロパティは状態・情報へのアクセスとして扱える設計であること。

## bool プロパティ

- bool 命名に対して `Is` `Has` `Can` 等の機械的強制は行わない。
- 状態・性質・条件・操作設定など、値が何を意味するのかを英語として判断する。
- 英語として不自然な接頭辞・接尾辞の使用は避ける。
- 同一責務においては、API を予測しやすいよう統一性を重視する。

---

# メソッド

- メソッド名は PascalCase とする。
- メソッド名は「〜をする／させる」という動作・処理を表す英文として命名する。
- 英文は略体でも構わない。
- メソッド名は原則として単語ではなく文章として命名する。
- `Load` や `Close` のような単語のみの名称は避ける。
- 動作対象・処理内容が分かる命名を優先する。
- async メソッドは末尾に `Async` を付加する。

---

# ローカル変数

- ローカル変数名は camelCase とする。
- 略語は原則として避け、文章として読める名称を使用する。

---

# メンバ変数

- private / protected メンバ変数名は `_camelCase` とする。
- メンバ変数はクラス内部の実装状態を保持するためのものとする。
- public メンバ変数は禁止する。
- 外部公開が必要な場合はプロパティまたはメソッドを使用する。
- やむを得ず public メンバ変数を定義する場合も `_camelCase` 命名を使用する。

---

# アクセス修飾子

- アクセス修飾子は最小公開を原則とする。
- 明確な理由がない限り private を基本とする。
- public は外部利用者に対する正式な API 契約として扱う。
- internal は同一アセンブリ内で共有する実装要素に使用する。
- protected は継承先に提供する正式な契約として扱う。
- protected virtual は任意の拡張ポイントとして扱う。
- protected abstract は派生クラスに実装を要求する責務として扱う。

---

# abstract / virtual

## abstract

- abstract は「継承先で定義する」を意味する。
- abstract メソッドは、派生クラスが必ず実装すべき責務を表す。

## virtual

- virtual は「継承先で定義して良い」を意味する。
- virtual メソッドは、基底クラスが正式に提供する任意の拡張ポイントとする。
- override されなくても基底クラスの動作が成立する設計とする。
- 継承を想定しないクラスは sealed を検討する。

---

# エラー処理

- 実行時エラー・異常状態は例外として扱う。
- 戻り値で扱うのは、ロジック上「処理を完了できない状態にある」「処理依頼が正常に成立しなかった」ことを表す結果のみとする。
- 戻り値による結果表現は、処理内容に応じて柔軟に決定する。
- bool による成功判定、結果クラス、構造体などを適宜使用してよい。
- 特定の Result 型や結果セット型の使用を強制しない。

---

# Collection 命名

- collection 命名は、そのデータの役割・見え方を優先して決定する。
- 一覧・列挙として扱う集合は `List` を使用してよい。
- `List` は一般語としての「一覧」を意味し、実装型を意味しない。
- 単純複数形で自然かつ明確な場合は複数形を使用してよい。
- まとまり・分類等を表現したい場合は `Group` 等を使用してよい。
- collection 命名は、型情報より意味の自然さと分かりやすさを優先する。

---

# enum 命名

- enum メンバ名に Prefix は付けない。
- enum 型名との組み合わせで自然に読める名称を使用する。
- enum が状態・分類・結果・命令のどれを表すかに応じて、英語として自然な名称を使用する。

---

# イベント関連

- `OnXxx` は「Xxx が発生した時の処理」を表すイベントハンドラ命名として扱う。
- イベント発火用メソッドとして `OnXxx` を使用しない。
- イベント通知用メソッドには `NotifyXxx` など役割を明示する名称を使用する。

---

# MVVM 方針

- 本規約では MVVM アーキテクチャを基本方針とする。
- Model は、状態・データ・業務制御を担う層として扱う。
- ViewModel は、UI の状態管理・操作制御・UI 間連携・機能単位の統括を担う層として扱う。
- ViewModel は View と 1 対 1 対応を前提としない。
- View は表示そのものを担う層として扱う。
- HTML / XAML / Prefab 等の表示定義自体を View として扱う。
- C# 側の UI 制御クラスは、View そのものではなく、View を操作・接続・制御する ViewModel 側の責務として扱う。
- 具体的なカテゴリ名・名前空間・フォルダ名・クラス名は、プロジェクト特性に応じて適切に設計する。

---

# Unity ライフサイクル

- Unity の予約メソッドは、原則として基底クラス側で管理する。
- 派生クラスから `Awake` `Start` `Update` 等を直接 override させない。
- 基底クラスは予約メソッド内部で必要な共通処理を実行し、派生向けに `OnXxx` 形式の protected virtual メソッドを提供する。
- 派生クラスは `OnXxx` のみ override し、自クラス責務のみを実装する。
- `base.Start()` 等の呼び出しを派生クラスへ要求しない設計を優先する。
